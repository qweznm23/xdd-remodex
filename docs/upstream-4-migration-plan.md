## XDD 自托管部署的兼容要求

用户已有通过局域网或公网 IP 加自选 TCP 端口直连的设备。每轮合并涉及配对、可信设备、网络策略、下载或发布配置时，都要按下表检查。示例使用文档保留地址，实际部署沿用设备已保存的地址。

| 手机操作 | 必须保留的行为 | 验收方式 |
| --- | --- | --- |
| 首次配对与已有设备重连 | 允许形如 `ws://203.0.113.10:10019/relay` 的公网 IP，也允许局域网 IP 和 10004 等自选端口。使用者可以直接部署，无需域名或 TLS 证书。配对身份校验、二维码有效期、会话加密和重连签名继续生效 | 在局域网和蜂窝网络各测一次扫码、打开会话、收发消息、断网重连；核对保存的协议、IP 和端口。另测原有 WSS 入口 |
| 健康检查、检查更新和下载 APK | 默认更新地址随当前设备的有效中继地址（含用户覆盖的主机）派生。`ws` 对应 `http`，`wss` 对应 `https`，保留有效端口。实际配置了更新转发时，手机通过同一入口访问 `/updates/update.json` 和相对 APK 地址 | 分别切换两个端口不同的设备，从 App 内下载，核对归属设备及 Range 响应；单独验证健康检查。内部更新源可只在回环监听 |
| 预览文件、下载附件和视频定位 | 已配置文件转发的部署经同一中继入口访问 `/files/stream`，保留传输授权、分段校验和续传；内部文件源保持在回环。聊天和重连可与下载同时进行 | 下载期间切换会话、重连、恢复已验证的偏移，验证无效授权被拒绝和视频分段读取 |

协议兼容和网络可达分别验收。健康检查返回成功只证明手机能访问中继；fix73 的安全协议 v1 对候选桥接 v2 仍会收到 `update_required`。实现 v2 时须沿用 Android 既有的自托管路由策略。使用 HTTPS/WSS 的设备继续使用其原有的 TLS 校验。

候选中继 HTTP、模拟配对重连、更新代理、文件代理及桥接文件流五组测试 43/43 通过，均使用本机隔离端口。Android Release 下的路由策略、二维码和更新地址三组单测 18/18 通过，覆盖公网 IP、自选端口和主机覆盖。局域网与蜂窝网络的真机验证待做。

## 迁移顺序和验收

| 阶段 | 实施内容 | 验收条件 |
| --- | --- | --- |
| 1 · 建立可比较的服务端基线，已执行 | 合并固定 SHA，保留两边的测试，用临时 HOME、Codex 目录和测试凭据运行。修复 Linux 桌面 Unix socket 首次初始化及重复查询账号触发的 Token 刷新 | 两个固定点均为候选祖先，Android 和 iOS 目录分别与各自基线一致；已知失败见下表 |
| 2 · 接回现有手机所用的接口，已完成服务端回归 | 授权与建议回复见 `350232d`，Android 原生分页与体积保护见 `f04f767`，Linux SVG 预览 MIME 修复见 `3778761` | 已用合成授权与模拟 Codex 验证桥接入口。原生历史测试覆盖问答字段、游标、与实时消息并发、缩页和下表中的文件读取探针。手机历史问答显示及操作留待端到端验证 |
| 3 · 打通 Android 协议 | 对照 v2 的握手签名、密钥派生、信封和重放处理，验证历史消息标识及缓冲缺口触发补读。用独立桥接和中继建立 v1/v2 客户端×旧/新服务四种组合的结果表 | 验证首次连接、已有信任重连、断线期间收到的消息，以及升级顺序。优先测试新版手机先连接旧服务再迁移；若旧手机不能访问新版服务，先提供可同时使用的旧入口，公开对应版本和升级步骤 |
| 4 · 功能和平台回归 | 覆盖模型列表、实时消息归属、置顶/已读、文件预览及下载、语音和更新入口。双方都修复过的行为按同一输入比较；新增会话目标、OpenCode 等分别评估 Android 的入口与实际收益 | 跑桥接、中继和 Android 相关用例，记录冷打开、重连补历史和边滚动边收消息的结果。Linux Unix socket 与独立启动模式分别验收；macOS 原生路径须在 Mac 验证。Android 重型验证与其他项目错峰 |
| 5 · 发布准备和后续维护 | 对照安装文档检查服务端包内容、客户端签名、版本号和更新地址，在测试设备按已验证的顺序升级并演练恢复 | 关键接口与跨版本矩阵通过后再合回主线并发布。旧服务端包和配置可恢复；Android 须考虑系统禁止较低 versionCode 覆盖安装，准备同签名且版本号可升级的恢复包或验证新版客户端能回连旧服务 |

下一阶段从断线恢复开始。v2 在 serverHello 中提供 `bridgeReplayEpoch`，通过加密的 `remodex/bufferedReplay/reset`、`gap`、`completed` 消息区分桥接进程重启、缓冲溢出及补发结束。fix73 的 resumeState 只发送上次应用的序号。验收要分别模拟同一进程重连、重启后序号重叠及缓冲区截断，核对当前会话、其他会话和实时消息的恢复顺序。

## 以后每轮如何同步

1. 在本地更新 `original` 的引用，登记上次合入和本轮候选的两个完整 SHA。按桥接、中继、协议和客户端行为审阅两点间增量。
2. 从 XDD 主线建立当轮候选，合并固定 SHA 并保留双亲历史。Android 特有功能通过单独提交接入，把双方行为差异写成入口测试。
3. 验收后以保留历史的方式合回主线，在发布说明记入上游 SHA、Android 与服务端配套范围和实测平台。下一轮从这个 SHA 继续。现有 GitHub 仓库继续作为发行仓库。
